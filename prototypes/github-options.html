Research and tradeoffs behind these options

The current view mixes repository browsing, the current branch, PR details, and workflow runs in one narrow area. These alternatives give each a clearer place. They preserve Herdr’s existing panel widths, underlined tabs, small controls, and separate preview pattern.

  • A · Current branch: shortest path when working on one PR. Inspired by GitHub Desktop’s branch-centered workflow. Other PRs remain available in the selector; the selected PR stays visible above its sections.
  • B · List + preview: strongest match for Changes and History. Keep the list visible and put longer reviews and logs in a separate pane. VS Code’s GitHub integration similarly combines PR browsing with editor-based review. This is my recommendation for Herdr.
  • C · Attention queue: fastest path to “what needs me?” across PRs and CI. Inspired by PostHog’s Herdr PR mod, which groups PRs by required attention and surfaces failed checks and unresolved threads. It gives scanning priority over browsing all PR metadata.
OptionStrongest useTradeoff
A · Current branchWorking on one PR at a time.Other PRs require the selector, and long reviews stay in a narrow panel.
B · List + previewMoving between PRs, reviews, and CI while keeping the list in view.The preview uses some of the terminal workspace.
C · Attention queueFinding the next failure or unresolved thread to address.Full PR descriptions take another step; less suited to browsing every PR.

Across all options: failed jobs come first, successful jobs start collapsed, review extraction is a named action, and PR identity stays visible. GitHub’s workflow log UI expands failed steps so the error is available without opening every successful step.
